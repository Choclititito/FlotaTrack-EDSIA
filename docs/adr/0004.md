# ADR-0004: Autenticación HTTP Basic con credencial única compartida para el front de empleados

## Estado
Aceptado

## Contexto
El front de captura de carta porte (`/empleados`) permite registrar/editar
datos fiscales de un viaje (`POST /trips/{id}/carta-porte`). Ese endpoint no
puede quedar abierto a cualquiera, pero el sistema no tiene (ni necesita para
el alcance del reto) una tabla de usuarios/empleados con altas, bajas ni
roles: es un equipo de 2 personas con 3 semanas y un solo perfil de empleado
que usa ese front.

## Decisión
Se usa **HTTP Basic** con una sola credencial compartida (`employee_username`
/ `employee_password`), definida por variables de entorno y nunca
hardcodeada. `require_employee_auth` (`app/security.py`) la valida con
`secrets.compare_digest` (comparación en tiempo constante, para no dar pistas
de timing sobre qué tan correcta es la credencial enviada) y protege:

- `GET /auth/check` — el front la llama al iniciar sesión para validar
  usuario/contraseña antes de mostrar el formulario.
- `POST /trips/{id}/carta-porte` — creación/edición de la carta porte.

El resto de la API (camiones, telemetría, conductores, lectura de viajes,
descarga del PDF) queda sin este candado, porque no expone edición de datos
fiscales.

## Alternativas consideradas
- **Cuentas individuales por empleado + JWT/sesión**: permitiría saber quién
  editó cada carta porte y revocar acceso a una sola persona. Se descartó
  por requerir un modelo `Employee`, flujo de login/registro y gestión de
  tokens — fuera de alcance en 3 semanas para un solo perfil de usuario real.
- **Sin autenticación**: más simple, pero cualquiera con la URL podría
  alterar datos fiscales de una carta porte ya generada.
- **API key en un header custom**: equivalente en seguridad a HTTP Basic,
  pero HTTP Basic ya trae integrado en el navegador el prompt de
  usuario/contraseña, evitando construir un formulario de login propio en un
  frontend estático sin framework.

## Consecuencias

**A favor:**
- Rápido de implementar, sin tabla de usuarios ni gestión de sesiones.
- `compare_digest` evita filtrar por timing qué tan correcta es la
  credencial probada.

**En contra / riesgos:**
- No hay trazabilidad de **quién** hizo cada cambio: todos los empleados
  comparten la misma credencial, así que la auditoría por usuario no es
  posible con este diseño.
- Rotar la contraseña obliga a avisar a todo el personal al mismo tiempo (no
  se puede revocar el acceso de una sola persona sin afectar a las demás).
- HTTP Basic manda la credencial en cada request; se depende de que el
  despliegue esté siempre detrás de HTTPS (Render lo da por default) para
  que esto no viaje en claro.
- No hay expiración de sesión: la credencial es válida indefinidamente hasta
  que se cambie por variable de entorno.
