# ADR-0005: FastAPI sirve ambos frontends estáticos; un solo servicio desplegado en Render

## Estado
Aceptado

## Contexto
El producto necesita dos interfaces web: el panel del despachador (mapa,
estado de la flotilla, viajes) y el front de captura de carta porte para
empleados. Equipo de 2 personas, 3 semanas, sin presupuesto para
infraestructura adicional, y la API también debe quedar consumible de forma
independiente (por el ESP32 hoy, y pensando en una futura app móvil según la
idea original del producto).

## Decisión
Ambos frontends son HTML/CSS/JS estático (sin framework de build), montados
directamente por FastAPI con `StaticFiles` en `/panel` y `/empleados`
(`app/main.py`), dentro del **mismo proceso y contenedor** que expone la
API. Se despliega como un solo servicio en Render, construido desde el mismo
`Dockerfile` que ya usa Alembic + Uvicorn.

## Alternativas consideradas
- **Frontend en un framework (React/Vue) desplegado aparte** (Vercel/Netlify),
  separado del backend: más flexible y escalable a futuro, pero duplica la
  configuración de despliegue, obliga a manejar CORS entre dos dominios de
  producción distintos, y suma una curva de aprendizaje de framework para un
  equipo de 2 personas en 3 semanas.
- **Server-side templating (Jinja2)** en vez de HTML/JS estático que llama a
  la API vía fetch: acopla más el frontend al backend. Se descartó para
  mantener la API consumible de forma independiente (necesario para el
  ESP32, y para no cerrar la puerta a la app móvil planeada a futuro).

## Consecuencias

**A favor:**
- Un solo servicio que desplegar, versionar y monitorear.
- CORS simple: solo hace falta autorizar el propio dominio de Render, más
  `localhost` y `null` (para abrir el HTML con doble clic durante
  desarrollo) — ver `app/main.py`.
- Cero costo adicional de hosting de frontend.

**En contra / riesgos:**
- Un solo punto de falla: si el proceso de backend se cae, ambos frontends
  dejan de servirse también.
- No hay CDN dedicado para los estáticos; todo sale del mismo dyno/contenedor
  que atiende la API.
- El frontend no puede escalarse ni desplegarse de forma independiente del
  backend con este diseño — si en el futuro se vuelve una app móvil, ese
  cliente sí necesitará consumir la API por separado (la API ya está
  pensada para eso, pero los dos frontends estáticos actuales no).
