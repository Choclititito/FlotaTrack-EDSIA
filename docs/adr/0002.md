# ADR-0002: Protocolo de kill switch remoto condicionado a velocidad cero

## Estado
Aceptado

## Contexto
FleetTrack permite al despachador bloquear/desbloquear remotamente un camión
como medida antirrobo (kill switch). Esta es una decisión con consecuencias
físicas reales, no solo de software: aplicar un bloqueo mientras el camión
va en movimiento podría causar un accidente. El sistema necesita decidir
**quién tiene la última palabra** sobre cuándo se ejecuta el corte: el
servidor (que pide el bloqueo) o el dispositivo en el camión (que sabe si es
seguro aplicarlo en este instante).

Restricciones: la comunicación entre el ESP32 y el backend not tieneconexión persistente ni confirmación
instantánea — el dispositivo solo "escucha" al backend cuando manda su
siguiente lectura de telemetría, lo cual introduce latencia inevitable
entre que se solicita un bloqueo y que se puede aplicar con seguridad.

## Decisión
El servidor **nunca fuerza** el corte. El flujo es:

1. El despachador solicita un bloqueo o desbloqueo (`POST /trucks/{id}/kill-switch`),
   lo cual crea un `Command` en estado `pending`. Si ya había un comando
   pendiente para ese camión, se cancela (solo el más reciente es válido).
2. En cada reporte de telemetría del dispositivo, el backend le informa si
   hay un comando `pending` para él.
3. El dispositivo decide cuándo es seguro aplicarlo. Cuando reporta una
   lectura con velocidad prácticamente 0 (`speed_kmh` ≤ umbral de seguridad)
   **y** confirma explícitamente el `command_id` que está aplicando
   (`acknowledged_command_id`), el backend marca el comando como `applied` y
   actualiza el estado de seguridad del camión.
4. Si el dispositivo confirma un comando pero reporta velocidad mayor al
   umbral, el backend **ignora la confirmación por completo** — el comando
   se mantiene `pending` y se le vuelve a informar en el siguiente reporte.
   No se confía en que el dispositivo ya validó esto por su cuenta: el
   backend revalida la condición de velocidad de forma independiente.

## Alternativas consideradas

- **Bloqueo inmediato desde el servidor**, sin esperar confirmación del
  dispositivo: más simple de implementar y con menor latencia, pero permite
  que un despachador (o un error de UI) corte un camión en movimiento. Se
  descartó por el riesgo físico que implica.
- **Confiar en que el dispositivo ya valida la velocidad antes de reportar
  la confirmación**, sin que el backend la revise de nuevo: reduce lógica en
  el servidor, pero deja la validación de seguridad enteramente del lado del
  firmware, que es más difícil de auditar y actualizar que el backend. Se
  descartó a favor de que el servidor sea la fuente de verdad que revalida
  la condición, incluso si el dispositivo también la checa.
- **Confirmación con contraseña o token físico en el camión** (ej. botón
  físico) en vez de solo velocidad: más seguro contra un servidor
  comprometido, pero fuera de alcance de hardware para 3 semanas.

## Consecuencias

**A favor:**
- Nunca se puede aplicar un bloqueo mientras el camión está en movimiento,
  sin importar qué tan rápido actúe el despachador o si hay un error en el
  dashboard.
- La regla de seguridad vive en el backend, un solo lugar fácil de auditar y
  de cubrir con tests (ver `tests/test_telemetry.py`), en vez de depender
  únicamente del firmware.

**En contra / riesgos:**
- Hay latencia entre que se solicita el bloqueo y que se aplica: en el peor
  caso, hasta el siguiente reporte de telemetría del dispositivo después de
  que el camión se detenga. Para un antirrobo esto es aceptable (mejor
  tarde que nunca, y nunca en movimiento), pero debe explicarse así en el
  video/documentación para que no se malinterprete como un bug.
- El estado `pending` puede quedar "colgado" indefinidamente si el camión
  nunca reduce su velocidad a 0 (ej. una fuga real donde el vehículo se
  robó y no se detiene). No hay todavía un mecanismo de escalamiento o
  alerta adicional para ese caso — queda como ítem de backlog a futuro.
- Requiere que el dispositivo (o su simulador) implemente correctamente el
  protocolo de confirmación; un firmware mal hecho podría nunca confirmar
  o confirmar de forma incorrecta.
