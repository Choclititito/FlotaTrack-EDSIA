# ADR-0006: SQLite en memoria para pruebas automatizadas, Postgres para desarrollo/producción

## Estado
Aceptado

## Contexto
El CI (GitHub Actions) corre `pytest` en cada push/PR y debe hacerlo rápido
y sin fricción de infraestructura. SQLAlchemy + Alembic ya abstraen el
dialecto de base de datos, así que en teoría el mismo código puede correr
sobre distintos motores.

## Decisión
`tests/conftest.py` fuerza `DATABASE_URL=sqlite:///:memory:` (con
`StaticPool` para que el `TestClient` reutilice la misma conexión en memoria
entre requests) **solo** durante `pytest`, con un fixture `_setup_db` que
crea y destruye el esquema en cada test para aislarlos entre sí. Postgres
16 sigue siendo la base real, tanto en `docker-compose.yml` para desarrollo
local como en producción.

## Alternativas consideradas
- **Postgres real también en pruebas** (vía testcontainers, o un servicio de
  Postgres dentro del workflow de GitHub Actions): más fiel al comportamiento
  real (tipos de datos, constraints, fechas), pero añade tiempo de arranque a
  cada corrida de CI y complejidad de configuración para un equipo de 2
  personas en 3 semanas.
- **SQLite en archivo** en vez de en memoria: evita depender de una sola
  conexión compartida (`StaticPool`), pero es más lento y deja archivos
  temporales que limpiar entre corridas.

## Consecuencias

**A favor:**
- Las pruebas arrancan y corren en milisegundos, sin levantar ningún
  servicio externo en CI.
- Aislamiento simple: cada test empieza con el esquema recién creado y vacío.

**En contra / riesgos:**
- SQLite no valida todo igual que Postgres (tipos más laxos, distinto
  comportamiento en algunas restricciones/fechas). Un bug específico de
  Postgres podría pasar `pytest` sin problema y solo aparecer al correr con
  `docker-compose` local o ya en producción — vale la pena probar
  manualmente contra Postgres antes de una entrega importante, no solo
  confiar en el CI.
